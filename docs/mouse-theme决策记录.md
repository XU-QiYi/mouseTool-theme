## 决策 1：主题数据存储在 LOCALAPPDATA

**结论**

```
%LOCALAPPDATA%\CursorStudio\
├── themes\
│   └── <theme-uuid>\
│       ├── theme.json
│       └── cursors\
│           ├── arrow.cur
│           └── ...
└── history.json      ← 使用事件流（「最近使用」由它派生），独立于主题存在
```

**为什么**

- 光标文件是二进制资源，不是用户文档。放进 `Documents` 会让"文档"目录里莫名多出一堆 `.cur` / `.ani`。
- `Documents` 可能被 OneDrive / 坚果云接管，一个 50MB 主题包会被同步上云并产生冲突副本。`LOCALAPPDATA` 天然不参与同步。
- 卸载后数据保留这一点，两个位置都满足（都在安装目录之外）。
- 代码里只允许存在**一个**根目录来源：`utils/paths.rs::data_root()`。

**代价与补偿**

用户找不到这个隐藏目录 → 需要一个「打开数据目录」入口（`explorer.exe`）。**已实现**：设置 → 数据分组的「打开数据目录」（`open_data_dir`，目录不存在先创建），侧栏「设置」已是第四个导航项，见决策 14。

**作废的旧说法**

- 需求文档 v1.0 的 `Documents/MyCursorTool/Themes/` 作废。
- 早期设想的 `cache\` 目录**不存在**：光标只在被查看时解析，结果放在后端内存 LRU（上限 64 条，按路径 / 修改时间 / 大小失效），前端另有同请求去重，均不落盘（见决策 4）。

## 决策 2：不写系统 Cursors 目录，不需要管理员权限

**结论**

导入和应用主题时，**不**把光标文件复制到 `C:\Windows\Cursors`。注册表 `HKCU\Control Panel\Cursors` 直接指向 `%LOCALAPPDATA%\CursorStudio\themes\...` 下的绝对路径。

`HKCU` 相关操作全部是普通用户权限，全程无 UAC 弹窗。

**为什么（这条很关键）**

1. `HKCU\Control Panel\Cursors` 的值允许指向任意可读路径，并非必须指向系统目录。系统目录只是第三方安装器的习惯做法。
2. **提权会让拖拽功能失效**。Windows 的 UIPI 机制下，以管理员权限运行的窗口收不到从资源管理器拖入的文件。一旦为复制文件而提权，拖拽就直接废了。这是二选一的取舍，拖拽更重要。

**附注：刷新只传 `SPIF_SENDCHANGE`**

```rust
SystemParametersInfoW(SPI_SETCURSORS, 0, None, SPIF_SENDCHANGE)
```

路径已由 `write_cursors` 直接写进注册表，此时只需让系统重新加载。若再带 `SPIF_UPDATEINIFILE`，系统会回写用户配置，本机实测返回 `0x80070006`（无效句柄），刷新直接失败。**别加回去。**

**已知的与权限无关的限制**

光标主题在**安全桌面**（UAC 提示框、登录界面、锁屏）上不生效，显示的是系统默认光标。这与文件放哪里无关，任何第三方主题工具都一样，不是本项目的缺陷。

**参考：本机现状**

当前系统里已安装的第三方主题文件位于 `C:\Windows\Cursors\荧1.0\`（由别的安装器放入）。本项目不采用这种方式。

## 决策 3：光标槽位共 15 个，顺序固定

**结论**

下表为**唯一权威定义**，代码里的 `SLOT_DEFS` 与之一一对应。

顺序只影响两件事：

1. **读** `Cursors\Schemes` 时按位置解析逗号分隔的路径（缺项留空但逗号不能省），位置错一项，整套光标就串位；
2. 导入 / 导出时的文件命名、以及界面上槽位的排列顺序。

**写**的时候按 `registry_key` 逐个写 `Cursors` 下的值，不依赖顺序；当前也**不写** `Schemes`（理由见需求文档 §4）。

| # | 注册表键名 | 中文名 | 英文名 |
|---|-----------|--------|--------|
| 1 | `Arrow` | 正常选择 | Normal Select |
| 2 | `Help` | 帮助选择 | Help Select |
| 3 | `AppStarting` | 后台运行 | Working in Background |
| 4 | `Wait` | 忙 | Busy |
| 5 | `Crosshair` | 精确选择 | Precision Select |
| 6 | `IBeam` | 文本选择 | Text Select |
| 7 | `NWPen` | 手写笔 | Handwriting |
| 8 | `No` | 不可用 | Unavailable |
| 9 | `SizeNS` | 垂直调整大小 | Vertical Resize |
| 10 | `SizeWE` | 水平调整大小 | Horizontal Resize |
| 11 | `SizeNWSE` | 对角线调整 1 | Diagonal Resize 1 |
| 12 | `SizeNESW` | 对角线调整 2 | Diagonal Resize 2 |
| 13 | `SizeAll` | 移动 | Move |
| 14 | `UpArrow` | 候选选择 | Alternate Select |
| 15 | `Hand` | 链接选择 | Link Select |

**顺序依据**

已在本机 `HKCU\Control Panel\Cursors\Schemes\firefly` 实测验证：15 项路径依次对应上述顺序（第 2、7、14 项为空）。解析时按位置取，不按文件名猜。

**槽位推断只对文件名生效**

导入时依次走：先 `EXACT_NAMES` 精确匹配短名（`no` / `ns` / `we` / `up`），再 `SLOT_KEYWORDS` 包含匹配。短名**绝不能**放进包含匹配表——`no` 会撞上 `normal`，`up` 会撞上 `upload`。

**超出 15 项的键**

现代 Windows 10/11 的 `Cursors` 键下还有 `Handwriting`、`Move`、`Location`、`Person`、`Pin` 等值，取值形如 `builtin://move.cur`。这些由系统管理，**本项目不读也不写**。

## 决策 4：`.ani` 预览用 Rust 提帧 + 前端 canvas

**结论**

导入时**不**转 GIF。需要预览时按需解析：

```
.ani (RIFF 容器)
  → Rust 拆 RIFF，取 anih 头 / rate 块 / LIST fram
  → 每帧本质是一个 .cur(ICO)，解码为 RGBA
  → 编码 PNG → base64
  → 返回 { is_animated, frames: [base64...], rate_ms, hotspot }
  → 前端 canvas 逐帧播放
```

**为什么**

- 不需要引入 GIF 编码器，也不用在磁盘上额外生成一堆 GIF 文件。
- 能同时拿到每帧的 rate 和热点坐标，播放速度和定位更准。
- 只保留一份原始文件，删主题时不会有残留。

**性能约束**

- 帧列表走 IPC 会占内存 → **后端内存 LRU（上限 64 条）+ 前端请求去重**（`useCursorPreview`，按文件路径去重 + 同请求合并）：缓存键是「路径 + 修改时间 + 大小」，删主题时按目录失效；同一光标只解析一次，不落盘。
- 单帧统一缩放到**最长边 128px** 再编码，避免 256px 高分辨率光标撑爆 IPC。
- 动态光标**最多取 32 帧**，超出截断。
- 解析失败不报错，返回 `{ is_animated: false, frames: [] }`，UI 显示占位图标。

**降级路径**

若某 `.ani` 结构异常解析不出帧，退回显示首帧静态图 + 「动态」角标。

**作废的旧说法**

需求文档 v1.0 的"导入时转 GIF 存盘（方案 A）/ 失败降级（方案 B）"整体作废，只保留"降级显示静态图"这个思路。

## 决策 5：WebView2 必须禁用沙箱（`--no-sandbox`）

**结论**

```json
// src-tauri/tauri.conf.json
"app": {
  "windows": [{
    "additionalBrowserArgs": "--no-sandbox"
  }]
}
```

**为什么**

本机 WebView2 的渲染进程沙箱无法初始化，表现为：窗口正常打开、进程存活、JS 与 `invoke` 全部正常工作（内核日志能看到 `console.log` 输出），但**不绘制任何像素**，整个窗口纯白。

加 `--no-sandbox` 后立即恢复，连 `.ani` 逐帧预览都正常。

**重要陷阱（务必记住）**

Tauri 自己会设置 `additionalBrowserArgs`，**它会覆盖 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 环境变量**。通过环境变量传 `--disable-gpu`、`--force-device-scale-factor`、`--disable-features=...` 等参数**完全无效**，必须写在 `tauri.conf.json` 里。

**安全评估**

`--no-sandbox` 关闭了 Chromium 的进程沙箱。本应用只加载本地打包的页面、不加载任意外部内容，风险可接受。若后续要收紧，可尝试 `--disable-gpu-sandbox` 等更精确的参数，找出最小必要集合。

## 决策 6：零新依赖，浮层用 base-ui 自封装

**结论**

`@base-ui/react` 已自带 `toast` / `alert-dialog` / `dialog` / `menu` / `popover`。需要这类能力时，**按 shadcn 风格手写封装**，不安装 sonner、radix 等平行实现。

- Toast 单例：`lib/toast.ts` 用 `Toast.createToastManager()` 建全局 manager，store / service 可直接调用。
- 渲染层：`components/ui/toaster.tsx` 挂在 App 根部。
- `import.meta.env.DEV` 下暴露 `window.__toast`，供自动化脚本触发验证。

**为什么**

同一个界面里不出现两套浮层实现，动效与层级（`z-60` / `z-50`）只需维护一处；也避免为了一个 Toast 多背一个库。

**作废的旧说法**

"Toast 需要安装 `sonner`"作废（架构文档旧稿、早期组件树提示词里都有，已删）。

## 决策 7：「正在使用」只从注册表反推

**结论**

`get_all_themes` 额外返回 `active_theme_id`：读 `Cursors` 各槽位当前路径，与所有主题的槽位路径双向比对（路径做大小写归一）。

**为什么**

用内存或 localStorage 记住"上次应用了哪个"必然过期：用户可能在系统设置里换方案、可能重装主题、可能手工改注册表。**注册表才是事实来源**。用本地状态会出现"已经用着的主题还能再点一次应用"这种明显错误。

识别不出时返回 `null`（系统默认光标，或用户手工改过设置），界面不显示"使用中"标记，而不是猜一个。

## 决策 8：最近使用独立存储，导出保持可回灌

**结论**

- 历史存 `%LOCALAPPDATA%\CursorStudio\history.json`，**不塞进 `theme.json`**。磁盘上是**事件流**（v2：`{version, events[]}`）：每次应用追加一条，上限 200 条，每条只存**名称快照**；同一主题反复应用就留多条事件，它回答的是「什么时候用过什么」。
- 界面要的「最近使用」是**派生视图**：从事件流按 `theme_id` 取最新一条、最多 50 个，由后端在读取与记录时统一派生，前端不自己折叠。两种语义不要混用——磁盘事件流不去重，`recent` 去重。
- **版本兼容**：v1 的 `{version, entries[]}`（按主题去重的旧清单）仍能读，每条旧记录当作一条事件，下次写入时升级为 v2；遇到不认识的更高版本只读不写并给出提示，避免把新版本数据覆盖掉。
- `apply_theme` 返回 `ApplyOutcome { recent, warning }`：光标切换是主操作，记历史是附属操作。**主操作成功就不回滚**，历史失败只带 warning 回去提示。
- `export_theme` 的包内文件名**按槽位重命名**（`arrow.cur` / `busy.ani`），不是源文件名。

**为什么**

- 主题随时会被改名或删除，历史必须能独立成立；靠 `theme.json` 存历史，删主题就把历史一起带走了。
- 事件流与「最近主题」分开：前者是事实（同一天反复切同一套也留痕），后者是界面问题（时间轴不该被同一套主题刷屏）。旧 v1 去重清单可以直接兼容读，因为它的每条记录本身就是「该主题最后一次使用」。
- 导出必须能"再导入回来"。导入端先认 `.inf` 映射、没有再按文件名推断槽位，用源文件名（如 `荧光指针-1.cur`）会让回灌后的槽位全丢。同名槽位按 `registry_key` 去重，跳过的项在 `ExportSummary.skipped` 里说清原因。

**细节**

- `history.json` 原子写：先写 `.json.tmp` 再改名；损坏时只降级为警告，下一次记录重建。
- 导出 zip **失败不留半成品、也不毁掉旧目标**：先写同目录临时包（主题导出 `.cursorstudio-export-<uuid>.zip`、备份 `.cursorstudio-backup-<uuid>.zip`），完整成功后才 `rename` 到目标；任一步失败删临时包，原目标文件保持原样。
- `capabilities/default.json` 用了 `dialog:*` 时，save 需确认 `dialog:allow-save` 在授权内，否则运行时才报权限错。

## 决策 9：导航三项对应三种视图，不是同一张列表的三个过滤条件

**结论**

三个导航项各有独立视图与任务，**不复用同一个列表组件**：

| 导航 | 视图 | 任务 | 右侧检查器 |
|---|---|---|---|
| 主题图库 | 分组网格（系统方案 / 我的主题 两段） | 逛、挑 | 有 |
| 我的主题 | 数据表（槽位覆盖 / 导入于 / 导出·删除） | 管 | 有 |
| 最近使用 | 按自然日分组的时间轴 | 回溯 | 没有 |

- 选中项**按页各记一份**（`selection: Record<Page, string | null>`）：切页回来还是原来的上下文，又不会把别的页的选择带过来。切页只清搜索词，不清选中。
- 全局「当前光标」状态卡常驻侧栏底部，「还原系统默认」只在这一处提供，不散落在详情区。

**为什么**

- 重构前三个页面共用 `ThemeList` + `ThemeCard` + `ThemeDetail`，差异只有一个 `filter` 和一句空状态文案 —— 点导航后中间区域几乎不动，用户会以为切换失灵。**这是结构问题，不是样式问题**，只改视觉救不回来。
- 同一个集合用两种视图看并不冗余：图库回答"哪个好看"，我的主题回答"我导入了什么、覆盖了几个槽位、要不要清掉"。Photos 的「图库 / 相簿」是同一个道理。
- 「最近使用」刻意不挂检查器：它只有时间这一条结构，多一栏只会把时间轴挤窄，也让人误以为可以在这里编辑。

**作废**：`ThemeList` / `ThemeCard` / `ThemeDetail` 三个组件已删除。新增页面时不要退回"一个列表 + 一个详情 + 过滤条件"的旧结构。

## 决策 10：不做自制方案与单光标替换

**结论**

- 产品定位收窄为「主题管理器」：**导入整套方案 → 应用 → 管理 → 回溯**。不提供在应用内制作或修改光标的能力。
- 连带不做：逐槽位上图、单光标替换、图片转 `.cur`、热点编辑。槽位卡保持纯展示、不可点，也**不做 hover 暗示** —— 别用视觉反馈引导用户去点一个点不动的东西。
- 主题来源只有两条：系统注册表里已有的方案、`.zip` 导入。

**为什么**

- 自制方案要同时新增三块能力：图片 → `.cur` 的写入与热点、15 个槽位的装配界面、以及"创建"这条与导入不同的落盘路径。成本远高于主线，而主线（浏览 / 应用 / 管理）才是这个工具存在的理由。
- 单光标替换与"主题不可变"直接冲突：改完要决定 `updated_at` 动不动、正在使用的主题要不要重新写注册表。为一个边缘功能引入一套状态语义，不划算。

**作废**：别再按"先做编辑器，主题自然就有了"规划。要解决"主题从哪来"，方向是**更多可导入的来源**（授权内容、索引 + 下载安装），最终仍然回到 `import_theme` 那条落盘路径，而不是在应用内生产光标。

## 决策 12：诊断与快捷入口落地，右键菜单按「先看效果」试点

- **`.zip` 右键菜单导入 = 试点**：
  - 设置页里**用户手动注册 / 移除**（不在安装时静默写系统），落在 `HKCU\...\SystemFileAssociations\.zip\shell\CursorStudio.Import`，命令为 `"exe" --import "%1"`，无需 UAC；

- **检查更新：不做**——没有任何可指向的版本源；等有发布渠道或版本清单 URL 再接（**决策 14 修订：发布通道定为 GitHub Releases 后已接入**，版本源即 Releases 最新 tag）。

**为什么**

- 系统级集成的"别扭不别扭"只有真机用出来才知道，纸上争论不出结果；试点做成用户可逆的手动开关，去留成本都低。

## 决策 13：导出 zip 附带通用 .inf，接收方不用装本软件也能用

**结论**（2026-10-22）

- `export_theme` 在包根额外生成 `<方案名>.inf`（光标文件之外唯一的附加文件）：**UTF-16LE + BOM、CRLF**，头部注释内含给接收方看的安装说明与 15 槽位对照表。
- 格式走 Windows 自 Win98 起的原生通道（社区光标包几十年通用格式）：`CopyFiles` 把光标复制到 `%SystemRoot%\Cursors\<方案名>\`；`AddReg` 写 `HKCU\Control Panel\Cursors\Schemes` 方案串——**严格按 `SLOT_DEFS` 的 15 槽位位序，缺失槽位留空段**——再逐槽位写值（只写本方案提供的槽位，不动接收方现有的其它光标）。接收方解压后右键 →「安装」即可。
- 口径：
  - 只收 `.cur`/`.ani` 槽位（`.ico` 不能被 Windows 当作光标加载，照常导出但不进 .inf，否则装出的方案「应用」时这些槽位会失效）；
  - 方案名经清洗（Windows 非法字符、INF 的 `%`/`;` 转义、保留设备名）后同时充当 zip 内文件名与安装目录名；zip 2.x 对非 ASCII 文件名自动置 UTF-8 标志，Explorer 任意语言系统都能正确解出；
  - ~~导入端仍然不解析 `.inf`~~（**决策 15 修订，2026-10-24 已实现**：导入时 `.inf` 优先于文件名推断，解析在 `utils/inf_parse.rs`）。导入链路仍只收 `.cur/.ani/.ico` 当光标，「导出 → 再导入」闭环不破坏——包内文件本就按槽位命名，`.inf` 映射与文件名推断结果一致。
- **尝试过「装完自动弹出指针设置」（`RunPostSetupCommands`），真机否决**：微软文档记载该指令存在，但 Win11 右键「安装」实测不执行它，指针窗口没出现；且该指令是知名的 INF 滥用面，出现在分享给陌生人的包里弊大于利 → **已移除**。安装只注册方案，不触发 `SPI_SETCURSORS`；立即生效由接收方在指针设置里选一次方案，或注销重登（逐槽位值已写入注册表，登录时自动生效）。`SchemeName` 仍写入，与 `apply_theme` 的落盘状态对齐。
- 安装时接收方需要过一次 UAC——复制进 `C:\Windows\Cursors` 是该格式的原生行为，所有光标包都如此。本应用自身的「无 UAC」约束（决策 2）不受影响。

**为什么**

- 分享是导出的核心场景之一，而接收方很可能没装本软件。候选里 `.inf` 是唯一「单文件、系统原生、零门槛」的载体：`.bat` 写注册表可行但 SmartScreen/杀软拦截率高、GBK 编码坑深；`.theme` 没有复制文件的能力（引用路径必须已存在），还牵连壁纸等无关设置；单独导出 `.inf` 又必须两件套，漏发光标即废。
- 塞进现有 zip 而不是新开导出入口：分享只发一件东西才不会漏；导入端本来就只认光标扩展名，多余文件零侵入。

**作废**：「导出包内只有光标文件」的旧口径作废；「导出 → 再导入」的闭环语义不变；「安装自动弹出指针设置 / 安装即生效」口径作废——.inf 安装只注册方案，生效靠接收方选一次方案或注销重登。

## 决策 14：设置分组化——侧栏切成「返回 + 分组」，行为设置落 settings.json

**结论**（2026-10-23）

- **设置不是一个页面五个区块，是五个分组页**：通用 / 快捷键 / 数据 / 系统集成 / 关于。进入设置后侧栏整体切换成「返回 + 分组列表」，点分组换内容页，页头标题跟随分组（`lib/settings-sections.ts` + `SettingsView.tsx` 的 `Record` 强约束，与 `lib/pages.ts` 同规）。返回键回到进入前的页面。
- **通用分组**：
  - **应用主题**（跟随系统 / 浅色 / 深色）从侧栏底部迁入——外观开关是设置项，不该跟导航抢地盘（**修订决策 11 的「暂留侧栏」**）；
  - **开机自启动**：写 `HKCU\...\Run`（带引号 exe 路径），状态以注册表回读为准，与右键菜单同口径「注册的是当前程序位置」；
  - **关闭行为**：直接退出（默认）/ 最小化到托盘。托盘图标**按设置动态创建移除**（左击回主界面、右键菜单退出），不留悬空图标；关窗拦截在 Rust 侧（`on_window_event` + `prevent_close` + hide）；二次启动对隐藏窗先 `ShowWindow(SW_RESTORE)` 再置前；
  - **主题存储目录**：默认 `<数据目录>\themes`，可换；`paths::themes_dir()` 统一解析生效值；防呆拒绝数据目录本身/上层与互为子目录。**搬迁的安全流程由决策 17 细化**（暂存 + 校验 + 原子切换 + 回滚，确认框与进度条），本决策只定「可换」这件事；
  - **自动检查更新**：启动时查一次 GitHub Releases，只在发现新版本时提示。
- **快捷键分组**：应用内快捷键（Ctrl+1~4 切页、Ctrl+O 导入、Ctrl+F 聚焦搜索）+ 总开关；**不做系统全局热键**（这是光标主题工具，全局抢键弊大于利）。清单与按键处理同源（`lib/shortcuts.ts`）。
- **数据分组**：数据目录 + 诊断信息（决策 11/12 原有）+ **数据备份**（整包导出 themes + history；恢复是**合并**语义——本地已有主题整套跳过，使用记录按「主题 + 时间」去重后补回，本地事件不被覆盖或删除）。
- **关于分组**：版本（`getVersion`）、开源地址（`XU-QiYi/mouseTool-theme`）、检查更新（对照 Releases 最新 tag 三段版本比较；没发过版 / 网络不通如实报错，不假装「已是最新」）。**决策 12 的「检查更新不做」就此作废**——发布通道定下来了，版本源就是发布通道本身。
- **设置的持久化分三处**，不搞大一统配置：行为类落 `settings.json`（Rust 也要读：关闭行为、主题目录、开关，`update_settings` 补丁语义）；外观留 `localStorage`（首帧落色要同步读）；自启动真相在注册表。**主题目录的覆盖值走 `paths::themes_dir()`**，全部 `theme_dir()` 调用点自动跟随。

**为什么**

- 设置页首版是「两区四卡」（决策 11），再往里加行为开关就会变成一屏滚不动的大杂烩；分组化之后每个新锚点只加卡片或加分组，不动骨架。
- 关闭到托盘 / 自启动 / 主题目录这类**行为**必须 Rust 可见（关窗拦截、路径解析、开机启动都在系统层），所以落 `settings.json`；外观是纯界面偏好，迁去 settings.json 反而会让首帧深色闪白。
- 备份做「合并恢复」而不是「整目录覆盖」：恢复是救回丢失的东西，不该顺手抹掉用户之后的新改动；要整包重来，删掉目录再恢复即可。
- **语言切换（候选设置项）不做**：工具面向中文 Windows 用户，右键菜单文案、`.inf` 注释、后端错误文案都是中文；半吊子 i18n 比没有更伤体验。维持「仅简体中文」的既定口径，多语言是独立工程，不做伪设置。

**作废 / 修订**：决策 11「外观三态暂留侧栏底部，不迁入设置页」作废（迁入「通用」）；决策 12「检查更新不做」作废（接 GitHub Releases）。「设置页两区四卡」的描述口径随本决策更新为五分组。

## 决策 15：导入时槽位优先级——有 `.inf` 听 `.inf`，没有才按文件名

**结论**（2026-10-24，用户拍板；**同日实现**，`utils/inf_parse.rs`）

- 包内带有 `.inf` 且解析成功 → 槽位映射以 `.inf` 为准，**优先级高于文件名推断**。
- 包内没带 `.inf`，或 `.inf` 解析失败 → 按现状的文件名推断兜底（决策 3 的 `EXACT_NAMES` / `SLOT_KEYWORDS`），不报错、不因此缺槽位。

**为什么**

- `.inf` 是主题作者写明的"哪个文件当哪个光标"，比猜文件名准；但流通的压缩包大量不带 `.inf`，文件名推断必须保留，否则这类包导入后槽位全丢。
- 「有则准、无则兜底」两条来源共存，不影响「导出 → 再导入」闭环（决策 8 / 13）。

**实现口径**（2026-10-24，原"开工前要先定的问题"就此关闭）

- **`.inf` 认哪些写法：三种都认**——① `[Control Panel\Cursors]` 段直写 `槽位=文件`；② 任意段里的 AddReg 逐槽位行 `HKCU,"Control Panel\Cursors",槽位,标志,路径`（段名不限定，本工具导出的 `[Scheme.Reg]` 即此写法）；③ `Control Panel\Cursors\Schemes` 方案串按 15 槽位位序取（缺失段留空）。同一槽位按 ① > ② > ③ 先到先得。
- **编码**：BOM 识别 UTF-16LE/BE/UTF-8（覆盖本工具导出）；无 BOM 按宽松 UTF-8 解码——GBK 无 BOM 文件的槽位键名是 ASCII、照常解析，中文文件名乱码对不上包内文件后按槽位退回文件名推断。**为此不引入编码库依赖**。
- **值里的 `%10%` / `%CUR_DIR%` 等变量不展开**：那是安装目标路径，与包内布局无关，取最后一段文件名到包里对号。
- **说明书指向的文件不在包里** → 该槽位放开给文件名推断兜底，不缺槽位；解析不出任何映射 = 完全现状（纯文件名推断）。
- 只认 `HKCU` 根的 AddReg 行，与本工具导出口径一致；`HKLM` / `HKR` 行忽略。

## 决策 16：文件夹导入与 zip 共用同一套导入流程

**结论**（2026-10-24，用户拍板；**同日实现**）

- 文件夹导入**复用 zip 的导入流程**：入口多一步分流——是压缩包就先解压，是文件夹就直接用——之后的检查、登记、入库与 zip 完全同一条路（`importer::import_source` 分发，共用 `persist_theme` 落盘核心）。
- 错误提示不需要另定：只有一套流程，报错话术天然只有一套，沿用现有口径（仅「压缩包里没有…」/「文件夹里没有…」按来源用词区分）。
- 失败清理半成品主题目录的逻辑两条路共用；源文件夹**只读**，光标复制进数据目录，原件留在原地。

**为什么**

- 检查与落盘规则只存在一份：以后修漏洞、加规则改一处，两种入口同时生效，不会出现「zip 能导、文件夹导不了」的行为分叉。
- 两套流程各自维护的成本高，时间长了必然渐渐不一致；而文件夹与 zip 的差异只有「解压」这一步，没有理由分开写。

**实现口径**（2026-10-24）

- **入口**：拖放收 `.zip` 与文件夹；选择对话框仍只收 `.zip`（Tauri 对话框无法同时混选文件与文件夹），Ctrl+O / 侧栏按钮维持原样。右键菜单导入（决策 12）仍只写 zip 路径，走 `import_source` 自动兼容。
- **前端不按扩展名预拦完整路径**：文件夹名可能带点（「我的主题.v2」）、前端也判不了路径是不是目录，zip / 文件夹 / 其它文件由 `import_source` 权威校验并给出精准文案；浏览器开发通路（只有文件名、没有路径）维持只收 `.zip`。
- **50MB 上限对文件夹同样生效**：按文件夹内光标文件（`.cur/.ani/.ico`）与 `.inf` 的总条目数、总大小计；zip 仍按包大小计。（2026-10-26 修订：`.inf` 也纳入 `ScanBudget`，避免说明文档绕过限额。）
- **主题名**：取文件夹名整体（「我的主题.v2」不吃掉 `.v2`）；zip 仍取去掉 `.zip` 后缀的 stem。
- 非 zip 文件给一句人话（「只支持 .zip 主题包或整个主题文件夹」），不再是「不是有效的 ZIP」。

## 决策 17：槽位路径相对化存储，主题目录迁移走暂存与回滚

**结论**（2026-10-25，用户拍板；同日实现）

### 17.1 磁盘存相对路径，运行时才拼绝对

- `theme.json` 的 `CursorSlot.file_path` **只写相对主题目录的路径**（统一 `/` 分隔，如 `cursors/arrow.cur`）；同一主题的文件不再重复带盘符与数据根，主题整体搬到哪都自洽。
- 读盘后由 `utils/theme_paths.rs::resolve_theme` 统一拼成运行时绝对路径，预览、应用、导出、注册表比对用的都是这份绝对路径。**「磁盘相对、内存绝对」是唯一口径**，别在界面层自己拼。
- 备份导出与恢复执行同一套重写：导出时把主题的 `theme.json` 改写成相对路径再入 zip；恢复后按**新根目录**重写一遍（旧备份里的绝对路径也在这一步落成相对），所以「导入备份 → 换主题目录 → 预览 / 应用 / 正在使用」仍然成立。
- **旧数据兼容**：遇到历史 `theme.json` 里的绝对路径照常读。搬迁或备份重写时按顺序尝试映射回新主题目录：① 路径本身就在该主题目录下；② 路径里含主题 UUID 段；③ 主题目录内唯一的同名文件。都失败才保留原绝对路径并给 warning，不静默丢槽位。
- 改名（`rename_theme`）也走 `write_theme_json`，保证落盘仍是相对路径；`updated_at` 语义不变（决策 14 附录 B）。

### 17.2 迁移 = 预检 → 暂存复制 → 内容校验 → 原子切换 → 重绑注册表 → 落设置 → 清源

- **预检**（`preview_themes_dir`）：只校验与统计，不碰任何文件。目标先 `canonicalize`（不存在的尾部保留、已存在的前缀解析成真实路径），随后拒绝：UNC / 网络共享、非绝对路径、重解析点（符号链接 / 目录联接 / OneDrive 占位，逐段检查）、磁盘根目录、数据目录本身或其祖先、数据目录内部（**默认目录除外**）、与当前目录互相嵌套、目标是非目录、**目标非空**（若其中已有同名主题，文案点名该主题）。
- **执行**（`set_themes_dir`）：所有内容先复制到目标同级的 `.cursorstudio-migrate-<uuid>` 暂存目录；复制时把主题的 `theme.json` 改写成相对路径；逐文件比对文件数与大小，非 `theme.json` 文件再做 FNV-1a 64 哈希（不引依赖）；`theme.json` 改做语义校验（ID 一致、槽位键一致、每个相对路径在暂存区真实存在、不得残留绝对路径）。校验全过后才 `rename` 成目标目录——同盘改名，切换是原子的。
- **切换后**：把注册表里仍指向旧根的槽位改写到新根并 `SPI_SETCURSORS`，随后才写 `settings.json`。**任何一步失败都回滚**：反向重绑注册表、删掉新目录（原本是空目录的恢复成空目录），源目录与设置保持原样；错误文案带「已回滚」。
- **只有全部成功后**才删源目录；删不掉只降级为 warning（新目录已生效，数据都还在）。
- **UI**：更换目录先弹确认框，展示源、目标、主题数、文件数 / 体积与扫描 warning；确认后按钮锁定为「迁移中…」，进度条按 `copy → verify → switch → registry → settings → cleanup → done` 推进（`themes-dir-progress` 事件）；失败保留对话框、给出原因与「重试迁移」，关闭不丢原目录。迁移期间「更改」「恢复默认」都禁用。
- 命令数 22 → **23**（新增 `preview_themes_dir`），`set_themes_dir` 返回 `{ settings, report }`，`report` 带重绑槽位数与 warning。

**为什么**

- 绝对路径把主题钉死在某个根目录上：一旦换存储目录或把备份恢复到新机器，预览全空、应用写出失效路径，「正在使用」也识别不出来。相对路径是唯一能跟着主题走的基准。
- 迁移最怕两件事：**覆盖用户已有文件**和**文件搬了设置没落**。前者用「目标必须为空 + 同名主题点名拒绝」堵死；后者用「设置最后写 + 失败全回滚」保证文件与设置永远一致。
- 先复制到暂存区再原子改名，避免中途失败留下半个主题目录；内容校验能提前发现复制损坏，而不是等用户应用主题时才发现光标打不开。

**作废 / 修订**

- 决策 14 的「换时整树搬迁：同卷改名、跨卷复制后删源」作废，迁移实现以本决策为准（暂存目录位于目标同级，切换始终是同盘改名）。
- 「`theme.json` 存运行时绝对路径」的旧口径作废；`CursorSlot.file_path` 的**运行时**值仍是绝对路径，但**落盘值**必须是相对路径。

## 决策 18：归档限额与 IPC 输入都在后端收口

**结论**（2026-10-25，随安全加固实现）

### 18.1 主题包与备份共用一套限额代码

- 唯一来源是 `utils/limits.rs`。两种包只在**常量**上不同，读取、记账、报错、清理走同一套逻辑：

| 包 | 解压总量 | 单文件 | 条目数 | 目录深度 | 条目名长度 |
|---|---|---|---|---|---|
| 主题包 `THEME_LIMITS` | 50MB | 20MB | 512 | 8 层 | 240 字符 |
| 备份 `BACKUP_LIMITS` | 1GiB | 64MB | 4096 | 10 层 | 240 字符 |

- **流式复制**：`copy_bounded` 每次读 64KB，超出预算立刻停止并返回中文错误，不把整个条目读进内存；`ArchiveBudget` 按实际写入字节记账，压缩包声明的大小不可信。
- **文件夹导入同规**：`ScanBudget` 用同一组 `THEME_LIMITS` 限制递归扫描的深度、文件数与总大小，不是「zip 有上限、文件夹随便进」。
- **超限即清理**：zip 解压临时目录、落盘到一半的主题目录、恢复备份本次新建的主题目录都在错误路径上删除，不留半成品。
- 归档条目名先过白名单（`safe_relative_parts`）：拒绝 `..`、绝对路径、盘符 / 冒号、控制字符、Windows 非法字符、结尾空格 / 点、`CON`/`NUL`/`COM1` 等保留名与超深路径；`.DS_Store`、`__MACOSX` 这类垃圾条目静默跳过。**整包拒绝，而不是跳过坏条目**——一个恶意条目足以说明这个包不可信。
- 预览源文件上限 8MB（`MAX_PREVIEW_BYTES`），光标文件读取 / 应用 / 导出上限 20MB（`MAX_CURSOR_FILE_BYTES`）。

### 18.2 前端传来的结构一律不信

- `utils/validation.rs` 集中做 IPC 校验，命令层只把错误原样交给用户：
  - `validate_theme_slots`：槽位键必须在 15 个标准槽位内、不得重复、路径必须是 `.cur/.ani/.ico` 且非空；
  - `ensure_theme_id_matches_dir`：用户主题 ID 必须是规范小写 UUID，主题目录存在且**目录名 = ID**，`theme.json` 里的 `id` 也必须一致；系统方案只要求 `sys_` 前缀且没有目录；
  - `ensure_cursor_file`：预览等**没有主题上下文**的调用，canonicalize 后必须落在主题根目录或 `%SystemRoot%\Cursors` 内；用户主题的应用 / 导出走 `ensure_cursor_file_in_theme`，必须落在**这套主题自己的目录**内；系统方案走 `ensure_readable_cursor_file`（Windows 允许已保存方案引用任意目录，只校验存在 / 类型 / 体积）。（2026-10-26 修订：原“主题目录或 `%SystemRoot%\Cursors`”只适用于预览与系统方案，用户主题已收紧到本主题目录。）
  - `preview_path_if_allowed`：预览路径先过同一套来源校验，再卡 8MB，不满足就降级为空预览而不是报错；
  - `validate_dest_path`：导出 / 备份目标必须有存在的父目录、`.zip` 后缀、文件名不含非法字符、不是目录；备份来源走 `validate_source_file`；
  - `sanitize_loaded_slots`：读盘时未知槽位、重复槽位、越出主题目录的路径丢弃并写入 warning，不让坏数据进入内存。
- **为什么**：`theme_id` 会参与字符串拼路径、`CursorTheme` 来自 WebView，两者都属于不可信输入；解压炸弹和路径穿越则是压缩包入口的经典事故。把限额与校验各收成一个模块，避免「主题包加了、备份忘了」这类漂移。

## 决策 19：重操作后台执行、进度可见、互斥立即失败

**结论**（2026-10-25，随命令异步化实现）

- **所有触及文件 / 注册表 / 进程的命令都进 `tauri::async_runtime::spawn_blocking`**，包括主题读写、预览解码、备份、设置、系统集成；命令本身保持 `async`，主线程只做参数搬运与结果转发。`spawn_blocking` 失败统一转成「××任务异常退出（…）」。
- **进度事件**：导入 `import-progress`、备份导出 / 恢复 `backup-progress`、主题目录迁移 `themes-dir-progress`；载荷是 `TaskProgress { stage, current, total, message }`（迁移沿用 `MoveProgress` 的阶段）。解压按条目推进，`ProgressThrottle` 只在百分比变化时发一次，避免大包每 64KB 都撞状态。
- **互斥**：`utils/ops.rs` 的全局 `try_begin(label)` 用 `try_lock`，导入、备份导出 / 恢复、主题目录迁移共用一把锁；冲突时**立即**返回「另一个操作正在进行（导入 / 恢复 / 迁移），请等它完成后再××」，不排队——排队会让用户连点两下后收到两次结果。前一个任务 panic 导致锁中毒时恢复内层，不让一次失败永久堵死后续操作。
- **界面配合**：导入按钮旁显示进度文案与 `current/total`，备份恢复显示阶段进度条，迁移确认框内显示阶段；按钮在对应操作期间禁用并带 `aria-busy`。

**为什么**：解压 50MB、恢复 1GiB 备份、复制整个主题目录都是同步阻塞活，放在 Tauri 命令线程会直接冻结窗口；进度事件是「没卡死」的唯一证据。互斥锁解决的是同一批文件被两个操作同时改写（半成品目录、迁移与恢复互相踩踏），失败要快、要说人话。

## 决策 20：交互安全要有反馈，无障碍是基线

**结论**（2026-10-25，随交互与可访问性改造实现）

### 20.1 每个动作自己忙，不搞全局转圈

- busy 状态按 `动作:主题 ID` 记（`actionBusyKey` / `withBusyFlag`）：应用、改名、删除、导出各自加锁，操作 A 不会把操作 B 的按钮一起禁用。重复点击在 store 层直接忽略，失败/成功后一定在 `finally` 里释放。
- 删除对话框在执行期间拒绝关闭、按钮显示「删除中…」；改名输入框与铅笔按钮同理；检查器与表格行的按钮都按同一份 busy 状态禁用，避免两处状态不一致。
- **导出默认文件名要清洗**：`sanitizeFileName` 去掉 `\ / : * ? " < > |` 与控制字符、结尾空格 / 点，Windows 保留设备名追加 `_`，最长 80 字符。主题名可以随便起，但落成文件名必须能用。
- **恢复备份前默认确认**：恢复是合并语义（不覆盖已有），但仍会写数据目录，先展示来源与说明再执行；迁移沿用决策 17 的确认框。
- **顶层 ErrorBoundary** 包住整个 App：渲染异常显示可读的兜底页与「重新加载」，而不是纯白窗口。
- **网络有边界**：检查更新 8 秒超时（`AbortController`，超时文案单独说明）；外链只允许 `https://github.com/...`，其余 `console.warn` + 提示「已阻止打开外部链接」，不走系统 opener。

### 20.2 无障碍与语义

- `Segmented` 按 **radiogroup + roving tabindex** 工作：`←/→` 循环切换、`Home/End` 到首尾，焦点跟随选中项；只有当前项 `tabIndex=0`，Tab 不会在三个按钮间逐个停留。
- 标题层级固定为 **页面 `h1`（PageHeader）→ 分组 `h2` → 卡片 `h3`（SettingCard）**，不靠字号冒充标题。
- `AniPlayer` 尊重 `prefers-reduced-motion`：降级时只画一帧并停止定时器，系统设置变化时实时响应；恢复后重新播放。动效规范见 `motion.md` §5。
- 光标预览图是**装饰性内容**（旁边已有槽位名称），一律 `alt=""`，不让读屏重复念文件名。
- 「最近使用」的文案统一为「使用记录」；时间用 `<time dateTime="YYYY-MM-DDTHH:mm:ss">` 表达（本地存储格式 `YYYY-MM-DD HH:mm`，分钟精度，由 `appliedAtMachine` 转成机器可读值）。

**为什么**：安全反馈的第一原则是「用户知道自己点的那一下有没有生效」；全局 busy 会让无关操作一起变灰，反而制造焦虑。键盘、标题、减少动态、图片替代文本是桌面应用的基本盘，不是加分项。

## 决策 21：测试不碰真实数据，CI 守住四条底线

**结论**（2026-10-25，随测试隔离与 CI 实现）

- **不碰真实 `%LOCALAPPDATA%`**：`utils/test_support.rs` 用 `tempfile`（dev 依赖，决策 27）提供临时目录，并生成最小 `.cur` / `.ani` fixture；测试用 `paths::use_test_roots` 把数据根临时指到临时目录，结束后恢复。

- 隔离键让注册表用例可以并行；只有确实共享同一个键的用例才需要自行串行（防中毒取回锁：`unwrap_or_else(|e| e.into_inner())`）。
- **CI**（`.github/workflows/ci.yml`）：`windows-latest` + Node 22 + Rust stable，依次跑 `npm ci` → `npm run build` → `cargo test`（`src-tauri`）→ `node scripts/design_audit.mjs` → `node scripts/doc_ref_check.mjs`。先 build 是故意的：`cargo test` 编译期不需要 dist，但保持与本地验证顺序一致，也顺手把前端类型错误挡在 CI 上。
- `design_audit.mjs` 改为按仓库相对路径输出，并在发现非 2px 网格间距、字号魔法值、裸时长、`transition-all` 时**以退出码 1 失败**，不再只是打印报告。

**为什么**：测试改真实光标会让开发者一边跑测试一边看到鼠标闪变，CI 上则直接污染 runner；临时目录 + fixture 让测试可重复、可并行。CI 不覆盖需要 WebView2 的界面脚本，但类型、后端、设计 token 与文档引用这四类回归能在提交时拦下。

## 决策 22：内容安全策略与 capability 最小权限

**结论**（2026-10-25，随安全加固实现）

- **生产 CSP**（`tauri.conf.json` → `app.security.csp`）：
  ```
  default-src 'self';
  img-src 'self' data: blob: asset: http://asset.localhost;
  style-src 'self' 'unsafe-inline';
  connect-src 'self' ipc: http://ipc.localhost https://api.github.com
  ```
  `data:` / `blob:` 用于光标预览，`asset:` + `http://asset.localhost` 保留 Tauri asset 协议；`style-src` 的 `unsafe-inline` 是 React/base-ui 内联样式的必要项；`connect-src` 的 `ipc:` 与 `http://ipc.localhost` 是 Tauri IPC，`https://api.github.com` 是检查更新。**生产不放行 `unsafe-eval`、不放开任意 http(s) 目标。**
- **开发 CSP**（`app.security.devCsp`）：在生产策略基础上增加 `script-src 'self' 'unsafe-inline' 'unsafe-eval'`（Vite / React Refresh 需要）与 `ws://localhost:1420`、`ws://localhost:1421`、`ws://127.0.0.1:1420`、`ws://127.0.0.1:1421`（HMR；1421 是 `TAURI_DEV_HOST` 模式下的 HMR 端口）。开发放宽只存在于 `devCsp`，不会带进打包产物。
- **capability 收窄**（`capabilities/default.json`）：
  - `opener:default` → `opener:allow-open-url`，scope 只允许 `https://github.com/*`。前端本来就有同一份白名单（`lib/open-external.ts`），现在 IPC 层再挡一次；
  - 去掉 `opener:default` 附带的 `allow-default-urls`（任意 http/https/mailto/tel）与 `allow-reveal-item-in-dir`（前端未使用，打开数据目录走后端 `open_path`）；
  - `dialog:default` + 重复的 `dialog:allow-save` → `dialog:allow-open` + `dialog:allow-save`。前端只用 open / save，不弹 message / ask / confirm。
- **`--no-sandbox` 保留**：生产 CSP 与最小权限都建立在 WebView2 能正常初始化的前提上；删掉它会整窗纯白（决策 5 / 硬约束 3）。

**为什么**：`csp: null` 等于放弃对注入脚本、外连地址和图片源的约束；`opener:default` 允许任意 http/https/mailto/tel 交给系统处理，`dialog:default` 还附带未使用的 message。前端白名单只能防住写错的调用，防不住被注入后的调用——CSP 与 capability 是第二道、也是进程边界上的那道闸。

## 决策 23：维护型界面不新增导航；应用内备份只管自己生成的

**结论**（2026-10-26，随 UI 一致性重构落地）

- **维护型界面不新增一级导航、不新增第六个设置分组**：
  - **诊断中心**是「设置 → 数据」里的任务层弹窗（可关闭 Dialog），入口是原「诊断信息」卡；只读（数据从现有 store 派生），不提供自动修复，复制报告在弹窗内完成；
  - **批量导入（导入中心）**是全局任务层弹窗（App 挂载），入口是侧栏「批量导入」按钮与拖入 2–20 个来源；串行执行、失败可单独重试；单文件导入（侧栏 / Ctrl+O / 拖 1 个）保持原链路不动；
  - **备份历史**是「设置 → 数据」的子视图（返回按钮 + h2，不新开 h1），侧栏保持「数据」选中。
- **应用内备份落数据目录 `backups\`**：`export_backup` 的 `destPath` 可空，空 = 自动命名（`cursorstudio-backup-YYYYMMDD-HHmmss.zip`，同秒加 `-2`/`-3`）写入 `backups\`；`list_backups` 只读 zip 中央目录列这里的内容（时间倒序、上限 200、损坏标 corrupt 保留可见）；`delete_backup` 只收文件名，拒绝路径穿越与链接。**导出到任意位置的备份不受历史管理**（文案要说明）。
- 命令总数随 `list_backups` / `delete_backup` 从 23 增至 **25**。

**为什么**：诊断、批量导入都是"正在做一件事"的任务上下文，做成页面会把一次动作抬成一级信息架构；备份历史虽然常驻，但它只服务「数据」这一组的事，做子页既保留入口又不扩大导航。备份历史只管 `backups\` 是安全边界：任意路径的删除入口一旦打开，路径校验的任何疏漏都会变成"删错用户文件"的事故。

## 决策 24：系统改写光标的检测与夺回

**结论**（2026-10-26，双显示器真机实验后落地）

- **实验事实**（全程 UIA 自动化，注册表逐步取证）：系统「鼠标指针样式」设置页（`ms-settings:easeofaccess-mousepointer`）选一次样式，会把 `Cursors` 的 15 个经典槽位**整体改写**为系统方案文件（如黑色 = `%SystemRoot%\cursors\*_r.cur`）并写 `Pin`/`Person`；`SchemeName` 反而残留本应用写入的旧值。经典「鼠标属性」面板的方案下拉只认「当前 15 槽位与 `Schemes` 列表条目精确匹配」，本应用不写 `Schemes`（见约束 ③），所以面板恒显「(无)」——不是 bug，是面板的匹配逻辑。**15 个经典槽位仍是运行时唯一真相**；新旧两套写入没有所有权、谁后写谁赢，不存在"锁住"方案；重新应用主题即可夺回。
- **聚焦重查**：新增 `get_active_state`（只读注册表 + 主题清单比对，不重读历史、不取 `ops` 锁），App 在窗口聚焦与启动时静默调用，回写 `activeThemeId` / `activeExternal` / `currentSlotsFilled`；失败静默保留旧状态——聚焦很频繁，不能因为一次读取失败弹提示。
- **状态卡三态**：正在使用（success 点）/ 系统默认（槽位全空）/ **被系统设置修改**（warning 点：槽位非空但匹配不到任何主题，副文案给出占用槽位数）。诊断中心「当前使用」项同步该判定（warning + 建议重新应用或还原）。
- **「还原系统默认」常可用**：不再因 `activeThemeId` 为空而禁用——被外部改写时恰恰是最需要它的时刻；`restore_default` 顺带清空 Win11 新指针键 `Pin` / `Person` 的残留（值已存在才清，不凭空创建；`clear_cursors` 因此需要 `KEY_READ | KEY_WRITE`）。
- **明确不做**：不写 `Cursors\Schemes` 换取经典面板显示方案名——那只能改面板显示，挡不住系统再次覆盖，还污染系统"已保存方案"下拉（约束 ③ 维持）。
- 命令总数随 `get_active_state` 从 25 增至 **26**。

**为什么**：固定 15 槽位仍是 Windows 光标的唯一公开接口（决策 3 的前提成立）；新旧冲突无法根治，能做的是**尽快发现 + 一键夺回 + 诚实告知**。此前"重启后左下角变无主题"的机制正是：系统改写注册表 → 应用内存里的 `activeThemeId` 无从得知 → 下次全量读取才暴露。锁屏 / 重启后系统是否按设置页选中态重写槽位尚未自动验证（需要用户手动锁屏），聚焦重查已覆盖"在系统设置改完切回来"的最常见路径。

## 决策 26：删除改为软删除，回收站放在数据根

**结论**（2026-10-28，随主题回收站实现）

- **删除 = 移入回收站**：`delete_theme` 把整个主题目录搬到 `%LOCALAPPDATA%\CursorStudio\trash\<条目 UUID>\`，并在条目里写一份 `.trash.json` 快照（`theme_id` / 名称 / 删除时间 / 槽位数 / 字节数）。条目 ID 与主题 ID 分开：同一主题删两次、或删完从备份恢复再删，都不会撞目录；原 `theme.json` 原样保留（仍是相对路径）。
- **上限 20 套 / 512 MB**：超出后按删除时间自动清理最早的条目；`delete_theme` 返回 `{ auto_purged, warning }`，界面把本次清理了几套、原目录残留或自动清理失败如实告诉用户。回收站是安全垫，不是第二份主题库——不能无限长。
- **四个命令**：`list_trash`（返回条目 + 当前限额）、`restore_from_trash`、`delete_from_trash`、`empty_trash`；命令总数 26 → **30**。`delete_theme` 的返回从 `void` 变为 `DeleteOutcome`，并纳入 `ops` 互斥（跨盘复制期间不跟导入 / 备份 / 迁移抢目录）。
- **恢复的校验**：条目 ID 必须是规范 UUID；快照与目录名一致；`theme.json` 可解析、`id` 与快照一致、不是系统方案、至少有一个槽位；当前主题目录里不能已有同 ID 主题（可能从备份恢复过）。任何一条不满足都拒绝恢复，但条目保留，可彻底删除。
- **损坏条目可见不可恢复**：快照缺失 / 损坏，或 `theme.json` 解析不出、ID 不符、自称系统方案、没有槽位时，列表标 `damaged` 并给出原因，恢复按钮禁用；`delete_from_trash` 仍可清理它。不把坏条目藏起来，也不假装能恢复。
- **跨盘**：主题存储目录可以换到别的盘，`rename` 报 `ERROR_NOT_SAME_DEVICE` 时走「复制 → 校验文件数与字节数 → 删源」；复制失败清理半成品、源保持原样；源删除不干净作为 warning 返回。
- **边界**：`trash\` 不参与主题列表、备份、最近使用与主题目录迁移；恢复后的主题落到**当前**主题目录，因此换过存储目录也能找回。自动切换映射不清空——主题恢复后原映射自动重新生效，删除期间设置页显示「主题已删除，请改选」。
- **界面**：入口在「设置 → 数据 → 回收站」子页（与备份历史同构，决策 23），不新增一级导航；删除确认文案从「无法撤销」改为「移入回收站，可恢复」，删除成功的 toast 说明去处与自动清理。

**为什么**：删除曾是应用里唯一的不可逆操作，而备份是手动的、恢复还是合并语义；误删一套主题只能靠事后找备份。回收站把「删错」从数据事故降级成一次点击可修复的操作，同时用固定上限和自动清理避免变成第二份主题库。把回收站放在数据根而不是 `themes\` 下，是因为主题列表与目录迁移会整体扫描 `themes\`；混在一起会让被删主题复活，或把回收站一并搬到别的盘。

## 决策 27：新增依赖按总成本判断，默认不加

**结论**（2026-10-28）

## 决策 28：保存并接管当前光标

**结论**（2026-10-28，随「保存当前光标」实现）

- **入口**：侧栏常驻「当前使用」卡只有在 `active_external`（槽位非空但匹配不到任何已知主题）时显示「保存并应用」；系统默认或已知主题不显示，避免无意义重复。不新增页面 / 导航。
- **捕获**：`save_current_theme` 读注册表当前非空槽位 → 新建 UUID 主题目录 → 逐槽位复制光标文件（`.cur/.ani/.ico`，单文件 20MB / 总量 50MB）→ `theme.json` 只写相对路径（决策 17）。同一源文件被多个槽位引用只复制一次；名称自动生成「当前光标 YYYY-MM-DD HH:MM」，可事后在检查器改名。
- **自动接管**：所有当前槽位都成功抄下来后，用现有 `apply` 链路写注册表 + 刷新 + 记历史，状态卡变为「当前使用中」，外部改写态被收编。**有槽位没抄全时只保存、不自动应用**：自动应用会把没抄到的非空槽位写成空字符串，反而改变用户当前光标；结果里给出 warning 和跳过原因，用户检查后可手动应用。
- **重复保护**：当前槽位与任一已知主题（系统方案 / 用户主题，槽位集合与路径完全一致）匹配时拒绝保存，避免把已在库里的主题再复制一份。
- **失败语义**：捕获失败清理半成品主题目录；自动应用失败保留已保存的主题并返回 warning；命令取 `ops` 锁，不跟导入 / 备份 / 迁移 / 回收站抢目录。命令总数 30 → **31**。
- **边界**：不写 `Cursors\Schemes`、不改系统光标目录、不需要 UAC；捕获的是注册表当前值（环境变量已展开），同一文件只按路径复用、不做内容哈希去重；不替代 `restore_default`。

**为什么**：决策 24 能检测「被系统设置修改」，但当时只能重新应用其它主题夺回，外部那套光标无法归档。用户常见路径是先在系统设置 / 第三方工具里配好光标，再打开本应用；没有捕获能力时，一应用别的主题这套配置就丢了。备份与回收站都只覆盖本应用管理的主题，捕获补的是「外部来源」这一块。

## 决策 29：光标守护——启动与系统改写后的自动恢复

**结论**（2026-10-28，随「光标守护」实现）

- **开关**：`settings.json` 新增 `cursor_guard_enabled`，默认 `false`；UI 在「设置 → 通用 → 外观」的「光标守护」卡，开关下方显示可恢复目标与「立即恢复」。
- **触发时机**（只有三类，全部事件驱动）：
  1. **启动后首次检查**：设置与主题列表都就绪、且注册表读取成功时，如果没有任何已知主题在用（系统默认或被外部改写），恢复一次；
  2. **运行期外部改写**：聚焦重查（决策 24）把 `active_external` 置为真时，按「一轮」恢复一次；同一轮失败不反复重试；
  3. **用户刚打开开关 / 点「立即恢复」**：立即评估一次；手动入口不受开关限制。

- **不抢**：`activeThemeId` 非空时一律不动；运行期不处理「系统默认」（手动还原默认不会被下一帧抢回去）；注册表读取失败时不动；主题列表读取失败时不动。
- **实现**：`lib/cursor-guard.ts` 只订阅 `themeStore` / `settingsStore`，复用 `refreshActive` 与 `applyTheme`（新增 `silent` 仅抑制「已应用」成功提示，失败与历史警告照常）；不新增命令、不新增依赖、不轮询、不写 `Cursors\Schemes`、不复制文件、不做后台服务。
- **验收**：`scripts/guard_check.mjs`（默认关 / 开启即恢复 / 重载启动恢复 / 外部改写恢复 / 还原不抢 / 关开关不动 / 手动恢复 / 自动切换优先 / 主题被删不恢复 / 读取失败不动作 / 无 JS 异常）；`settings.rs` 往返与旧文件兼容用例。

**为什么**：决策 24 已确认系统设置页会整体改写 15 个槽位，重启后也可能掉主题；当时只做到「尽快发现 + 手动去图库重应用」。用户为了找回光标要切页、搜索、再点应用，而系统改写往往是随机的。守护把「发现 → 恢复」合成一步，正好补在核心承诺（应用后一直有效）上。自动切换只解决「深浅色该用哪套」，不负责「当前这套被抹掉后夺回」；两者一个管选择、一个管恢复，互不替代。

**为什么默认关闭**：自动改系统光标必须是用户明确同意的事——若用户正在系统设置里主动换样式，守护会把它抢回来。开关文案写明启动时也会恢复，避免「我明明还原了默认，重开又回来」的误解；需要登录后恢复时再配合开机自启动。

**边界**：
- 不保存 / 不接管外部光标（那是「保存当前光标」的职责，决策 28）；守护只恢复主题库里的已知方案。
- 不监听注册表、不做系统服务 / 计划任务；应用没运行就不会恢复。
- 不改应用规则：缺槽位仍写空字符串；不写 `Schemes`、不锁系统设置。
- 自动切换关闭且最近主题已删除时，守护静默不动作，设置页显示原因与禁用入口。

## 决策 30：托盘快速切换——驻留托盘时的最近主题直达

**结论**（2026-10-28，随「托盘快速切换」实现）

- **范围**：仅「关闭行为 = 最小化到托盘」时存在的托盘图标，右键菜单新增主题区：最近使用的主题（按事件流派生的去重视图，上限 8 个，当前正在使用的置顶并勾选）+「还原默认光标」（注册表槽位全空且读取成功时勾选）；「打开主界面」「退出」与左键单击开窗的行为不变。
- **复用**：托盘应用走 `commands/theme.rs` 的 `apply` 同一条链路（槽位白名单、UUID 与目录一致性、光标文件落点校验、注册表写入、`SPI_SETCURSORS`、记历史），还原走 `restore` 同链路；不新增命令、不新增依赖、不改任何 IPC 契约（命令新增的 `AppHandle` 参数由 Tauri 注入，前端无感知）。
- **菜单时机**：数据在重建时读取，不轮询注册表。重建时机 = 启动（初建菜单只有「打开 / 退出」，主题区随后台重查补齐，启动路径零 I/O）/ 关闭行为变更（`tray::sync`）/ 托盘内应用或还原 / 界面侧应用主题、还原默认、保存当前光标、删除主题、改名、回收站恢复 / 彻底删除 / 清空、备份合并恢复完成。重建放独立线程，注册表与磁盘 I/O 不进主线程。
- **过期自愈**：菜单是重建时拍下的快照，点击时主题可能已被删除——`apply_by_id` 从最新清单复核，找不到返回「未应用」并重查菜单摘掉条目，不报错、不动注册表；应用失败（如光标文件被挪走）记日志不弹窗——托盘没有 toast 通道，不为它引通知依赖（决策 9）。
- **展示口径**：菜单标签取主题清单里的**当前**名字（改名后菜单跟着变），历史记录里的名字只是快照；最近主题上限 8 个，全量挑选回主界面做。
- **验收**：`tray.rs` 的 `plan_theme_actions` 纯函数单测（死条目摘除 / 当前主题置顶勾选 / 上限 / 改名跟随 / 空清单）+ `theme.rs` 的 `apply_by_id` 隔离单测（应用并记历史 / 已删除静默跳过 / 校验不被绕过 / 还原清空槽位），注册表与数据根全部隔离。
- **边界**：不做托盘内预览、不做菜单内主题管理、不做全局热键（需新插件）；不写 `Cursors\Schemes`、不复制文件；光标守护与自动切换的行为不受影响——托盘应用与界面应用产生完全相同的注册表与历史状态。

**为什么**：托盘是「最小化到托盘」用户唯一的常驻入口，而切主题是这个应用最高频的动作；现状托盘只有「打开 / 退出」，驻留却开窗才能换光标，是驻留体验最明显的缺口。菜单数据事件驱动重建（对齐决策 29 的哲学）+ 点击时复核，保证不轮询也不过期误操作。

## 决策 31：主题文件完整性——缺口的提示，不是拦截

**结论**（2026-10-29，随「主题文件完整性体检」实现）

- **范围**：`get_all_themes` 聚合时对每套主题（系统方案与用户主题一体）的每个**非空**槽位做一次 `metadata` 存在性检查（`theme_paths::missing_slots`），读不到的槽位键名收进 `ThemesResult.file_gaps`（`ThemeFileGap { theme_id, slots }`，保持声明顺序）。命令数保持 31，不新增命令、不新增依赖。
- **口径**：**空槽位不算缺口**——那是主题没提供这个槽位（部分覆盖，`SlotMeter` 已有口径），与「提供了但文件丢了」是两回事。只查「文件在不在」，`metadata` 失败（不存在 / 权限不够 / 被独占）都算缺口；**不读文件内容**——内容损坏由预览占位图兜底，列表阶段逐个打开 20MB 上限的光标文件代价太高。
- **不落盘**：`file_gaps` 每次读列表现算，`theme.json` / 备份 zip / 注册表都不写它；文件恢复（放回、回收站恢复、备份补回）后缺口自动消失，无需清理动作。`#[serde(default)]` 兜住「前端旧、Rust 新」的热更新组合，前端读 `?? []`。
- **提示三处**：「我的主题」槽位列行内「缺 N 个文件」（管理任务在这里比对）；检查器头部动作条下方警示条，点名缺失槽位中文名并写明后果——**应用会把缺失槽位写成空字符串**（决策 3 的写入规则），这是应用前必须看见的信息；诊断中心第五项「文件完整性」（warning 级，逐主题给证据行）。
- **只展示不拦截**：应用 / 还原 / 导出等命令行为完全不变——缺口主题照样可以应用（用户可能只想用它覆盖还在的槽位），拦截是替用户做决定。应用路径的确认对话框留待真实反馈再议。
- **性能与范围**：每次列表加载多 N×槽位数 次 `stat`（微秒级，无内容读取）；托盘菜单与 `get_active_state` 不做这步（它们用不到，聚焦又很频繁）。诊断中心检查数据依旧全部从 store 派生，不新增命令。
- **验收**：`theme_paths.rs` 单测（缺失标记 / 文件齐全为空 / 空槽位不算缺口）+ `scripts/integrity_check.mjs`（正常态无提示 → 诊断「正常」→ `?mock-broken-files=1` 行内提示 → 检查器警示条点名中文名 → 诊断「注意」并点名主题 → 无 JS 异常）。
- **边界**：不做自动修复、不做文件内容校验、不做「应用前确认」弹窗；文件缺口不改变导入、应用、删除、备份与托盘的任何行为。

**为什么**：光标文件在应用数据目录里，用户完全可以手动删改；外部工具也可能动它。现状主题文件丢了没有任何前置提示——预览静默变占位图，直到某次「应用」把缺失槽位写成空字符串、半套光标凭空消失才被发现，且没有一条信息解释为什么。把「文件在不在」变成列表加载时顺带的只读体检，是诊断中心「从现有 store 派生、不新增命令」哲学的自然延伸。

## 决策 32：自动备份——每天一份进「备份历史」

**结论**（2026-10-29，随「自动备份」实现）

- **范围**：「设置 → 数据」的数据备份区新增「自动备份」卡：开关（`settings.json` 新增 `auto_backup_enabled`，默认 `false`）+ 保留份数 `auto_backup_keep`（默认 10，合法 1–100，UI 下拉只给 5/10/20）。开启后每天第一份备份以 `cursorstudio-backup-auto-YYYYMMDD-HHmmss.zip` 落进应用内 `backups\`，与手动备份同内容（`themes\` + `history.json`）、同限额（`BACKUP_LIMITS`）。
- **触发**（前端 `lib/auto-backup.ts`，只有三类，事件驱动）：设置与主题列表就绪后一次；窗口聚焦（节流 30 分钟）——常驻托盘的日子靠这个补上；开关从关拨到开当场补一份。当日去重、过期清理、与手动备份的互斥都在命令层，前端只管触发，多余调用只是一次目录扫描。
- **命令层**（新增 `run_auto_backup`，命令总数 31 → **32**）：取 `ops::try_begin("自动备份")`（与手动备份共用一把锁，同时触发时自动方立即失败、前端静默忽略）；扫 `backups\` 按文件名里的日期段做当日去重（不依赖修改时间）；落盘成功后按 keep 从旧到新清理 `auto` 前缀条目，**手动备份一份不碰**；不发 `backup-progress`，自动备份不顶掉手动备份的进度展示。
- **展示**：`list_backups` 的 `BackupEntry.kind` 按文件名前缀判定（`cursorstudio-backup-auto-` = `"auto"`），备份历史里显示「自动」徽标；恢复 / 删除 / 损坏标注与手动备份同一套。
- **失败语义**：「没有可备份的内容」（空库）与重操作锁占用视为正常态静默忽略；其余失败每次会话只警告一次（`toast.warning`），不轰炸，下一个触发点再试。
- **验收**：`backup.rs` 单测（当日去重 / 清理只动 auto 条目 / kind 判定，数据根沙箱）+ `settings.rs` 新字段往返与旧文件兼容 + 保留份数校验；`scripts/auto_backup_check.mjs`（默认关 / 保留份数随开关禁用 / 开启即出「自动」条目 / 当日去重 / 重载启动触发 + 清理到保留数 / 手动备份不牵连 / 关闭落盘 / 无 JS 异常）。

**为什么**：回收站（决策 26）只兜「误删除」——磁盘故障、目录迁移翻车、误清空回收站都会让主题永久丢失，而主题包往往是收集来的，丢了很难找回。手动备份已经存在，但依赖用户记得点；「每天一份 + 自动清理过期」把备份从动作变成机制，恢复语义完全复用决策 11 的合并式恢复。

**为什么默认关闭**：每天写一份 zip 是可感知的磁盘写入，不该在用户不知情时发生；保留份数默认 10、上限 100，空间代价可控且由用户决定。

**边界**：只备应用内数据（themes + history），不含设置与回收站（`trash\` 不参与备份，决策 26）；备份历史仍受 200 条列表上限约束；不做增量 / 差异备份、不做备份到云端或自选目录的自动化。

## 决策 33：定时切换主题——按时间段的自动应用

**结论**（2026-10-29，随「定时切换主题」实现）

- **设置**：`settings.json` 新增 `schedule_switch_enabled`（默认 `false`）、`schedule_start` / `schedule_end`（`HH:MM` 24 小时制，默认 09:00 / 18:00，后端 `validate_hhmm` 严格校验）、`schedule_in_id` / `schedule_out_id`（期间内 / 期间外主题，`None` = 该时段不切换，空串 = 清空，沿用决策 25 的映射语义）。UI 在「设置 → 通用 → 外观」的「定时切换主题」卡：开关 + 起止时间 + 两个映射下拉 + 窗口状态行。
- **触发**（前端 `lib/schedule-switch.ts`，不轮询）：设置 / 主题列表就绪或被修改；窗口聚焦（电脑跨过边界后才回来的兜底）；`setTimeout` 到下一个 start / end 边界（设置变化后重排，最长间隔 24h，不会触到定时器上限）。状态机、挂起、去抖与 `auto-switch.ts` 同构。
- **区间口径**：半开 `[start, end)`；`start === end` 视为空窗口（等于不切换）；`start > end` 视为跨零点（如 22:00–06:00 按两段拼接）。
- **优先级**：**时间段内且期间内主题已设置时，定时切换拥有这个时段，跟随系统切换让位**（`auto-switch.ts` 读 `scheduleOwnsNow`，决策 25 的深浅色配对在这段时间不动作）；窗口外深浅色照旧。挂起规则一致：手动「还原默认」后挂起，改设置或跨过下一个时间边界才解除；映射指向的主题被删除时静默跳过。
- **复用**：应用走 `applyTheme` 同一链路（busy、历史、托盘刷新全一致），不新增命令、不新增依赖；`cursor-guard`（决策 29）语义不变。
- **验收**：`settings.rs` 时间段字段往返 + `validate_hhmm` 用例；`scripts/schedule_check.mjs`（默认关 / 全日窗口命中 / 状态行判定 / 空串清空 / 还原不抢 / 关开关不动 / 改设置解除挂起 / 跨零点窗口按当前时刻判定 / 时间段内深浅色让位 / 关掉后深浅色接管 / 无 JS 异常）；`auto_switch_check.mjs` 全量回归。与决策 25 同构的启动竞态（settings 先就绪、列表为空时评估被 `lastAppliedId` 去重吞掉）一并修复，`schedule_check.mjs` 增补同样的竞态回归两步。

**为什么**：决策 25 解决的是「环境明暗」这个维度，真实需求还有「时间」维度——上班用低调方案、下班换炫彩的。两者都是「自动替用户应用主题」，必须明确只有一个说了算：按「定时窗口优先」仲裁，避免两个机制在同一分钟互相覆盖。

**为什么默认关闭**：自动改系统光标必须用户明确同意（同决策 29）；且默认时段（09:00–18:00）未必符合任何人的真实作息，开了不配映射等于没开，不如关着让用户自己配好再开。

**边界**：不做多时段 / 按星期几的复杂计划；不与光标守护联动（守护仍按自身规则恢复「上次主题」）；时段边界跨过时电脑若关机，开机后的首次评估（启动 / 聚焦）会补上正确主题；不写 `Schemes`、不复制文件。

## 决策 34：备份内容浏览与单主题恢复——恢复粒度从整包降到一套

**结论**（2026-10-29，随「备份内容浏览与单主题恢复」实现）

- **入口**：「设置 → 数据 → 备份历史」每一份可读备份的操作列新增「查看内容」（图标按钮）。打开任务层弹窗列出备份里能恢复的主题：名称、槽位数、文件数、缺文件数、解压后体积、导入时间；已在主题库里的主题标「已在主题库」并禁用恢复，零槽位主题标「没有槽位」且不可恢复，声明槽位全部缺文件的主题标「没有可用文件」且不可恢复。不新增导航、不新增设置分组（与决策 23 的维护界面同规）。
- **两个新命令**（命令总数 32 → **34**）：
  - `list_backup_themes(path)`：只读中央目录与 `theme.json`，**不解压光标**；返回 `BackupThemeListing { themes, warnings }`，沿用 `collect_complete_themes` 的完整性判定（id 与目录一致、不是系统方案、`theme.json` 可解析），并按包内实际条目算每个主题的 `missing_files`（旧绝对路径先按主题 id / 文件名归一化，空路径不算缺口）。
  - `restore_theme_from_backup(zipPath, themeId)`：只解压请求的那一套主题，追加到当前主题目录；返回 `RestoreBackupThemeOutcome { theme, warnings }`，`theme` 的槽位路径已解析为运行时绝对路径。
- **缺文件口径**：`missing_files` 只数 theme.json 声明、包里找不到对应文件的槽位，和决策 31 的「只查存在性」同口径；**部分缺文件仍可按套恢复**，恢复结果的 `warnings` 点名缺失槽位，落库后由完整性体检继续展示缺口；**全部声明槽位都没有文件时命令层直接拒绝**（恢复出来也是一套空主题），并清理本次新建目录。
- **追加语义**：目标主题目录已存在（含符号链接 / 目录联接）时直接拒绝，不覆盖、不改名、不碰原目录；不合并使用记录、不改设置、不影响备份里的其它主题。成功后才刷新托盘菜单（决策 30）。
- **落盘口径**：与整包恢复一致——旧备份的绝对路径先按主题 id、再按文件名映射到新根目录，最终 `theme.json` 仍写相对路径；读回后经 `sanitize_loaded_slots` 清掉未知 / 重复 / 越界槽位，再过 `validate_theme_slots`（15 槽位白名单与光标扩展名）；零槽位或全缺文件主题恢复失败并清理本次新建目录。
- **安全边界**：全部走 `BACKUP_LIMITS`（1GiB / 单文件 64MB / 4096 条目 / 10 层）与条目名白名单；`themeId` 必须是规范小写 UUID；取 `ops::try_begin` 锁（与导入 / 备份 / 迁移 / 回收站互斥）；命令 `spawn_blocking`，不发进度事件（单套恢复由弹窗行级 busy 表达）。只读阶段不执行任何写操作。
- **失败语义**：目标已存在、备份里没有该主题、`theme.json` 损坏 / ID 不一致、零槽位、全部槽位缺文件、写盘失败都返回可直接行动的中文错误；已开始解压的失败会删掉本次新建的主题目录，不留半成品。损坏的备份在读取内容时即报错；单套主题损坏只进 `warnings`，不影响其它主题列出。
- **验收**：`backup.rs` 单测覆盖列出主题与体积、缺文件计数、部分缺文件恢复提示、全缺文件拒绝并清理、只恢复选中一套、旧绝对路径映射、目标已存在拒绝且不碰原目录、找不到主题、零槽位清理、损坏 zip；`scripts/backup_content_check.mjs` 覆盖备份历史 → 内容弹窗 → 已在库禁用 → 缺文件标记（`?mock-backup-partial=1`）→ 恢复一套并提示缺口 → 列表重读并选中 → 重新打开仍显示已在库 → 无 JS 异常。

**为什么**：自动备份（决策 32）让 `backups\` 里可能同时存在多份日期快照，而现有恢复只有「合并整包」——要么把当天缺失的主题全部复活，要么为了找一套主题先把整包恢复再逐套删掉。备份内容对用户也是不透明的：只看到「几套主题」，不知道具体是哪几套。把浏览做成只读、把恢复粒度降到一套，正好补在「备份可验证、误删可精准找回」这一块，且完全复用既有归档限额、完整性判定、路径改写与互斥模型，不引入新依赖。

**边界**：不改 `import_backup` 的合并语义，也不把它替换成单主题恢复；不做备份内光标预览（那需要解压整套主题，代价与风险不该压在浏览上）；不合并历史事件，恢复后主题不会自动成为「最近使用」；不做备份编辑 / 删除单套主题 / 定时恢复；UI 入口只覆盖应用内备份历史，外部 `.zip` 仍走「从文件恢复」整包合并（命令层本身接受任意合法备份路径，未来可在文件选择流程复用）。

## 决策 35：维护工具箱——存储统计 / 批量导出 / 清空记录

**结论**（2026-10-29，随「维护工具箱」实现；2026-10-30 合入时与决策 34 撞号，重编为 35）

> 原型是四个能力（含备份内容预览 `peek_backup`）；合入时决策 34 的 `list_backup_themes` 已覆盖「恢复前知道包里有什么」且更完整（缺口清单 + 单主题恢复），`peek_backup` 让位删除，维护工具箱收敛为三条。

三个维护类能力一次落齐，全部长在既有页面里，**不新增导航、不新增页面**（决策 23 的任务层 / 子页口径不变）：

- **存储占用统计**：新命令 `get_storage_stats`（只读，不取 `ops` 锁），返回数据目录各区域（主题库 / 备份 / 回收站 / `history.json` / `settings.json`）的条目数与字节快照。条目口径：主题 = 含 `theme.json` 的一级子目录、备份 = `.zip`、回收站 = 含 `.trash.json` 的条目；孤儿文件计入字节但不冒充条目数。UI 是「设置 → 数据」的「存储占用」卡，挂载统计一次 + 手动「重新统计」——数字是快照不是实时账本。
- **批量导出**：新命令 `export_all_themes(destDir)`，逐套复用单套导出链路（`export_to`，含 `.inf` 附带与槽位命名），只导「我的主题」。落盘名后端兜底（非法字符 / Windows 保留名 / 重名加序号且不覆盖已有文件）；**部分成功**：单套失败（文件缺口、源被占）进 `failed`，其余照常落盘；拒绝把落点设进备份 / 回收站 / 主题库。取 `ops` 锁并发 `export-all-progress` 事件；UI 是「我的主题」工具条的「导出全部」+ 进度行，批量导出期间行内导出 / 删除让位（第二把锁会立即失败，别让用户撞上去）。

**为什么**：自动备份（决策 32）与回收站（决策 26）让数据会持续增长，但除了备份历史 / 回收站两个子页的局部数字，用户看不到全貌，也缺少「一键带走」「隐私清理」这些维护动作。三个能力都是数据管理的收尾一环：看清楚（统计）→ 拿得走（批量导出）→ 清得掉（清记录）；「恢复前知情」由决策 34 的备份内容浏览承担。

**为什么这样排序**：两个只读 / 轻量命令零风险先落，唯一写盘的批量导出复用最成熟的导出链路放最后；每个能力都刻意停在「维护」边界内——统计不做自动清理，批量导出不做过滤条件，清记录不碰主题与设置。

**验收**：Rust 单测覆盖三个命令的核心口径（分区域累计、零目录、路径穿越拒绝、重名加序号、部分成功、管理目录拒绝、清空计数与不创建文件）；`scripts/maintenance_check.mjs` 走浏览器 mock 验收三处 UI（统计行 / 批量导出提示 / 清空后「最近使用」变空）。

**边界**：不做定时自动统计（数据会变，快照语义说清楚即可）；批量导出不含系统方案（它们不在主题库里，导出单套已支持）；清空记录不提供「只删某一条」（事件流的最小维护单位是整份文件，加单条删除是另一个决策）。

## 决策 36：`.theme` 光标方案导入——Windows 主题方案收编为我的主题

**结论**（2026-10-30，随「`.theme` 光标方案导入」实现）

- **入口**：`import_theme` 的 `sourcePath` 分发新增第三类（决策 16 的 zip / 文件夹之外）：`.theme` 文件。侧栏 / Ctrl+O 的文件对话框 filter 放开 `.theme`，拖拽通路的浏览器白名单同步放开（完整路径本就交给后端权威校验）。
- **解析**（`utils/theme_file.rs`，纯函数）：`.theme` 是 INI 文本，光标方案在 `[Control Panel\Cursors]` 段——**键名与 `HKCU\Control Panel\Cursors` 的槽位值名同名**（Arrow / Help / AppStarting / Wait / NWPen / No / SizeNS / SizeWE / SizeNWSE / SizeNESW / SizeAll / UpArrow / Hand / Crosshair / IBeam），直接映射到 15 槽位白名单，不做翻译表；空值 = 槽位保持系统默认（不出现）。`[Theme]` 段的 `DisplayName` 作主题名，`@dll,-id` 本地化引用读不出真名、退回文件名 stem。编码与 `.inf` 同一套 BOM 识别（UTF-16LE/BE、UTF-8、无 BOM 宽松 UTF-8），1MB 文本上限（`read_bytes_bounded`），禁止先按 UTF-8 解码。值清理：去成对引号、去尾部 `,index` 后缀（防御注册表方案串写法）。
- **收编 = 复制**（语义同决策 28 的「保存当前光标」）：每个引用按 `%Var%` 环境变量展开（大小写不敏感；展不开的变量原样保留、按文件不存在处理）→ 绝对路径直接用 / 相对路径以方案文件所在目录为基准（`.themepack` 解开后光标与 `.theme` 同目录）→ 通过光标扩展名白名单与重解析点检查后，按槽位复制进新主题目录（复用 `copy_slots`：单文件 20MB 上限、按槽位重命名落盘）。源文件留在原地，不写 `Schemes`、不碰注册表。
- **部分成功**：引用缺失 / 展不开 / 非光标格式 / 链接联接只跳过该槽位并进 `warnings`（点名槽位中文名与原值）；**全部槽位落空才拒绝**（「方案文件里没有可用的光标条目」），失败清理半成品目录。落盘走决策 17 的相对路径口径。
- **不新增命令、不新增依赖**：命令数保持 37；INI 解析手写（`.inf` 已有同类解析器与 BOM 识别，`.theme` 复用 `decode_text`）。`.themepack`（CAB 容器）**暂不收**——CAB 解档需要引入新依赖（如 `cab` crate），按硬约束 9 需单独决策，当前先覆盖「`.theme` + 同目录光标」这一最常见形态（Windows 个性化「保存」出的方案、主题包解压后的目录都长这样）。
- **验收**：`theme_file.rs` 单测覆盖 UTF-16LE / ANSI、大小写不敏感键映射、空值、未知段键、本地化 DisplayName、引号与逗号后缀、注释；`importer.rs` 单测覆盖端到端导入（DisplayName 优先、缺文件警告、全缺拒绝且不残留、非光标文件跳过、环境变量展开、相对路径基准）；`scripts/scheme_import_check.mjs` 走浏览器 mock 验收 store 直导（stem 命名 + 检查器选中）、拖拽白名单放行 / 白名单外拒绝（新文案）、`.theme` 与 `.zip` 混拖进导入中心串行成功；`dnd_check.mjs` 增补 `.theme` 放行断言。

**为什么**：主题来源目前只有「别人打包好的 zip / 文件夹」与「注册表当前态收编」两条路，而 Windows 生态里现成的第三类资产被漏掉了——个性化设置保存的 `.theme`、微软商店 / 主题站分发的方案文件、`.themepack` 解开后的目录，都是「槽位 → 文件」的现成映射。`.theme` 的段键与注册表槽位名完全同名，收编成本几乎为零；收编成**普通用户主题**（复制文件）而不是运行时引用，与决策 17 的相对路径口径、决策 26 的回收站 / 备份语义天然自洽——方案原文件在哪、以后还在不在，都不影响主题库。

**为什么收编而不是安装**：`.theme` 里的引用大多是 `%SystemRoot%\cursors\` 的系统光标，直接「应用方案」等于把系统光标注册成当前值——用户拿不到可管理、可备份、可删除的主题实体。先收编为我的主题，用户再决定应用与否，与「保存当前光标」（决策 28）的心智一致。

**边界**：不做 `.themepack`（CAB 解档需新依赖，另行决策）；不做壁纸 / 声明 / 图标等非光标段的任何处理（不是本工具的业务）；不做方案文件预览（收编后主题检查器就是预览）；引用解析失败不做「同名猜测」兜底（方案里的文件名是权威映射，猜出来的映射错得悄无声息，比缺槽位更糟）。

## 决策 37：备份完整性体检——CRC 校验把静默损坏当场点名

**结论**（2026-10-30，随「备份完整性体检」实现）

- **命令**：`verify_backup(fileName)`（命令总数 37 → **38**），与 `delete_backup` / `peek_backup`（已让位）同一套「只收文件名、拒绝路径穿越 / 链接」的校验。实现是把 zip 里每个文件条目**流式读进 sink**——zip-rs 在读完时核对 CRC，坏数据当场报 `Invalid checksum`；不落盘、不驻留内存（1GiB 上限内的流式读取）。返回 `BackupVerifyReport { file_name, entries_checked, bytes, corrupt, corrupt_total }`：损坏条目名最多列 20 条，`corrupt_total` 保有总数。
- **只读、不取锁**：体检不改变备份的任何状态，与 `list_backups` / `get_storage_stats` 同为只读命令；并发删除正在体检的备份会得到「读不出来」的诚实报错，不用锁去挡（挡了反而把导出 / 恢复卡住）。
- **UI**：「备份历史」行内新增「体检」（盾形图标按钮）：完好包 toast「体检通过（N 个条目）」；损坏包 toast 警告并点名第一处损坏，行内出现「体检损坏 N 处」徽标（`data-backup-verify="damaged"`）。体检结果**是快照不是档案**：只在本次会话的组件状态里记损坏结论，重挂载即失效——备份列表随时可能被自动备份改写，持久化一个「上次体检通过」反而会骗人。已标 `corrupt`（中央目录都读不了）的行禁用体检，`list_backups` 已经说明它坏了。
- **定位**：`list_backups` 的 `corrupt` 只覆盖「打开就炸」的包（中央目录损坏）；zip **数据区**的静默损坏（下载断传、磁盘坏块、拷贝中断）在列表与预览里完全看不出来，要等到恢复那天才炸。体检把这一层补上：`备份（11/32）→ 预览 / 恢复（34）→ 统计 / 导出（35）→ 可验证（37）`。
- **验收**：`backup.rs` 单测覆盖完好包通过（条目数 / 字节）、STORE 条目翻一字节点名 `Invalid checksum`、穿越 / 缺失 / 非 zip 拒绝；`scripts/backup_verify_check.mjs` 走浏览器 mock 验收行内入口 → 完好通过无徽标 → `?mock-backup-corrupt=1` 注入损坏报告 → 徽标 + 警告 toast → 无 JS 异常。

**为什么**：备份的价值在「恢复那天」才兑现，而恢复失败是最坏的失败时机——用户正处在数据丢失的当口。CRC 体检让「这份备份还能不能用」变成当场可验证的事实，而不是一个从未被检验的假设。恢复（决策 34）会拒绝全缺文件的主题，但那是「包能读、内容缺」；体检覆盖的是更底层的「包内容坏了」。

**为什么放行内而不进诊断中心**：诊断中心（决策 23）目前是「打开即汇总、全部从 store 派生」的零命令模型，整库体检要对每份备份做全量 CRC（1GiB × N 份），会把诊断变成一次分钟级的阻塞。行内按需体检的成本与单份备份成正比，用户对哪份重要心里有数；真要整库扫，逐份点体检就行，界面不用为此改成异步报告模型。

**边界**：不做定时 / 自动体检（静默写盘的后台扫描与「快照语义说清楚」的口径冲突，需要时另立决策）；不做修复（CRC 损坏不可修复，结论是「重新备份」）；体检结果不落盘、不进诊断报告复制（复制报告只含打开即得的 store 数据）；`.theme` 方案与主题包导入不做体检（50MB 以内的包在导入时整包过流，坏了当场炸，不存在静默期）。

## 决策 38：主题内容去重诊断——「内容相同」用字节证实，不靠名字猜

**结论**（2026-10-30，随「主题去重诊断」实现）

- **命令**：`find_duplicate_themes()`（命令总数 38 → **39**），返回 `DuplicateReport { groups, scanned, skipped_missing, wasted_bytes, warnings }`；每组 `DuplicateGroup { theme_ids, theme_names, bytes, slots_filled }` 是内容完全一致的 ≥2 套「我的主题」，按可省字节（`bytes × (n−1)`）降序。只读命令，不取 `ops` 锁、不发事件。
- **两步比对，只报证实的重复**：先按「槽位键 + 扩展名 + 字节数」指纹（排序后比对）预分组——绝大多数不同包在这一步就分开；指纹相同的组内再与首套**逐字节比对**（64KB 分块，读不出的一律按不一致处理）。不做哈希、不引依赖：包内容是用户自己的光标文件，误报的代价（删错主题）远高于多读几遍文件，宁可保守。
- **比对口径**：只比非空槽位的**文件内容**，不看主题名 / 描述 / 导入时间 / 空槽位集合之外的差异；槽位文件缺失的主题**不参与比对**（`skipped_missing` 计数并在证据里指去「文件完整性」）——内容不完整不能断言重复。系统方案不参与（不在主题库里）。
- **UI**：诊断中心第六项「重复主题」（顶部摘要格从 4 列改 3 列，六项两行）。诊断中心原本是「全部从 store 派生」的零命令模型，这项是**第一个按需命令**：打开弹窗 / 点「重新扫描」时跑一次，比对中摘要显示「正在比对…」，结果只在本次弹窗会话内有效（库随时会变，持久化一个「无重复」反而会骗人）。无重复时证据写清口径；有重复时逐组点名成员、槽位数与单套体积，合计可省字节，建议「每组删到剩一套」（删除先进回收站）+ 跳转「我的主题」。
- **不自动删除**：查重只诊断。删除是破坏性动作，且「留哪套」是用户的偏好（留最老的？留名字顺眼的？），界面只把成员按 ID 排序点名，动作留给用户。
- **验收**：Rust 单测覆盖内容一致成组、同尺寸不同内容不成组（字节比对拦住指纹碰撞）、缺文件主题排除、三套成一组且可省字节按 n−1 累计；`scripts/duplicate_check.mjs` 走浏览器 mock 验收六项齐全、默认无重复、`?mock-duplicates=1` 注入后摘要与严重度变化、详情点名成员与可省字节、无 JS 异常。

**为什么**：决策 35 的存储统计回答「占了多少」，回答不了「哪些是白占的」——同一主题包改个名再导一次、从不同渠道收了同一套、`.theme` 方案与 zip 各导一遍，都会在主题库里留下内容完全相同的副本。靠名字找不出来（名字可以随便改），靠导入时间也不可靠；只有文件内容一致是可证实的。查重把「清理主题库」从凭感觉变成有依据。

**为什么指纹预分组还要逐字节确认**：指纹（键 + 扩展名 + 大小）相同不代表内容相同（改一个字节大小不变）；但逐字节比对只在指纹相同的组内做，最坏情况（整库都是同一套）也就是把库完整读一遍，常态下绝大多数主题指纹互异、成本接近零。不用内容哈希同理：省一次全库读取，代价只是重复组内多读几遍，而正确性是精确的。

**边界**：不做自动清理 / 一键去重（删哪套是用户决定）；不比对系统方案（它们没有文件实体）；不比对主题元数据（名字不同但内容相同就是重复，反过来名字相同内容不同不是）；诊断中心这一项是快照语义，不进「复制报告」之外的任何持久化；不做「部分重复」（只有部分槽位相同的提示——怎么合并是另一个决策）。

## 附录 A：技术栈定格

**Tauri 2 + React 19 + TypeScript + Vite + Tailwind CSS 4 + shadcn/ui（base-nova / `@base-ui/react`）+ zustand + Rust**。

选型理由（当年四选一的结论，其余方案不再考虑）：

| 方案 | 结论 |
|---|---|
| **Tauri（选中）** | 复用系统 WebView2，产物只有几 MB；前端生态直接可用；系统调用交给 Rust |
| Python + CustomTkinter/PySide6 | 开发最快，但打包 50–100MB，界面特效上限低 |
| C# + WPF/WinUI 3 | 最原生，但 XAML 学习成本高，且与现有前端代码零复用 |
| Electron | 生态最好，但内置整个 Chromium，体积与内存都不可接受 |
